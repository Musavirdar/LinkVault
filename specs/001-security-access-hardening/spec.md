# Feature Specification: Security, Access Control & Quality Hardening

**Feature Branch**: `001-security-access-hardening`  
**Created**: 2026-10-27  
**Status**: Draft  
**Input**: Comprehensive security remediation and quality audit addressing unauthenticated static uploads, cross-tenant file sharing, missing rate limiting, upload validation and stored XSS risks, hardcoded secrets, audit log leakage, and lack of automated tests.

---

## Clarifications

### Session 2026-10-27
- Q: How should the new authenticated file download endpoint authenticate browser requests when replacing the unauthenticated `/uploads/...` static mount? → A: Hybrid Ticket/Bearer: Primary endpoint accepts Bearer JWT header, but also accepts a short-lived single-use ticket (`?ticket=...`) generated by an authorized client for native browser download links.
- Q: How should audit log access be scoped for non-admin users (Members)? → A: Admin Only: Restrict audit log endpoints strictly to the Admin role (`[Authorize(Roles = "Admin")]`). Standard Members receive 403 Forbidden.
- Q: How should SVG file uploads be handled to balance user experience and XSS security? → A: Force Download / Attachment: Permit SVG uploads, but serve them exclusively with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, forcing browsers to download rather than execute inline scripts.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Secure and Authorized File Access (Priority: P1)

As an organization member, I want all uploaded documents and attachments to require organization-level authentication and directory permission checks before downloading, so that sensitive files and AI-retrieved knowledge cannot be accessed by unauthorized external parties or cross-organization users.

**Why this priority**: Directly secures data privacy. Plain static file serving at `/uploads/{userId}/...` is a severe data breach vulnerability that breaks the core guarantee of LinkVault ("answers respect permissions").

**Independent Test**: Can be verified by attempting to access a known file URL anonymously (must return 401/404) versus authenticated as an organization member with directory read rights (must succeed) versus an authenticated user from a different organization (must return 403 Forbidden).

**Acceptance Scenarios**:
1. **Given** an anonymous user possessing a valid file path or resource identifier, **When** they request the file via HTTP GET, **Then** the server denies access with 401 Unauthorized or 404 Not Found without streaming the file content.
2. **Given** an authenticated user belonging to Organization A, **When** they attempt to download a resource belonging to Organization B, **Then** the system rejects the request with 403 Forbidden and audits the violation.
3. **Given** an authenticated user with valid directory read permissions in Organization A, **When** they request an authorized file via the authenticated download endpoint using either a Bearer JWT header or an authorized short-lived single-use ticket (`?ticket=...`), **Then** the server retrieves the file stream via the storage provider and serves it with security headers (`X-Content-Type-Options: nosniff`).

---

### User Story 2 - Organization-Scoped Resource Sharing (Priority: P1)

As an authorized user with sharing permissions, I want share link creation to verify that the resource belongs to my active organization and that I have the required sharing privileges, so that users cannot generate public share links for arbitrary or cross-tenant resources.

**Why this priority**: Prevents unauthorized data exfiltration and cross-tenant privilege escalation where any authenticated user could guess an ID and share another organization's confidential files.

**Independent Test**: Can be tested by having an authenticated user in Org A attempt to generate a share link for a resource in Org B (must return 404/403) and by having a user without the `CanShare` permission attempt to share an Org A resource (must return 403).

**Acceptance Scenarios**:
1. **Given** an authenticated user attempting to create a share link for a resource ID, **When** the target resource does not belong to the user's current organization, **Then** the request is rejected with 404 Not Found or 403 Forbidden.
2. **Given** an authenticated user whose role lacks the `CanShare` policy, **When** they request creation of a share link, **Then** the endpoint enforces policy authorization and responds with 403 Forbidden.
3. **Given** an authorized user with `CanShare` rights targeting an organization-owned resource, **When** they create a share link with optional expiry and password, **Then** the share link is registered with organizational tenancy recorded.

---

### User Story 3 - Protection Against Brute Force and Rate Limiting (Priority: P1)

As a security administrator, I want authentication and two-factor verification endpoints protected by strict rate limits, so that credential stuffing and brute-force attacks against user accounts are mitigated.

**Why this priority**: Defends against automated credential guessing and 2FA token brute-forcing on exposed endpoints.

**Independent Test**: Send 10 rapid authentication requests within 30 seconds from a single IP/identity; requests exceeding the configured limit (e.g., 5-10/min) must be throttled with HTTP 429 Too Many Requests.

**Acceptance Scenarios**:
1. **Given** a client sending requests to login or 2FA verification endpoints, **When** request frequency exceeds the defined threshold (10 requests per minute), **Then** subsequent requests return 429 Too Many Requests with a `Retry-After` header.
2. **Given** normal legitimate user interaction within allowed limits, **When** authentication requests are submitted, **Then** requests are processed without throttling latency.

---

### User Story 4 - Safe File Upload Validation & XSS Prevention (Priority: P2)

As a workspace administrator, I want all uploaded files validated by server-side content sniffing (magic bytes) and sanitized content headers, so that malicious executable files, disguised scripts, and stored SVG XSS payloads cannot compromise user sessions.

**Why this priority**: Client-supplied `ContentType` headers are easily spoofed; serving raw SVGs on the API origin allows full JavaScript execution in user browser contexts.

**Independent Test**: Upload an SVG file or a file with an image extension containing malicious script payloads; verify that dangerous file types are rejected or forced to download as `Content-Disposition: attachment` with `nosniff`, and valid files with null directories associate properly with the root hierarchy.

**Acceptance Scenarios**:
1. **Given** an upload payload claiming an image content type, **When** the server inspects the initial byte headers (magic bytes) and detects a mismatch, **Then** the upload is rejected with a 400 Bad Request.
2. **Given** an uploaded SVG file, **When** downloaded or viewed by an authorized user, **Then** the response forces `Content-Disposition: attachment; filename="..."` with `X-Content-Type-Options: nosniff`, preventing in-browser script execution.
3. **Given** a file uploaded without an explicit directory ID (null), **When** persisted in the database, **Then** the directory foreign key is stored as nullable `null` rather than an invalid non-null `Guid.Empty`.

---

### User Story 5 - Environment-Driven Secrets & Startup Validation (Priority: P2)

As a DevOps engineer, I want all critical secrets (JWT signing keys, database passwords) to be sourced strictly from environment variables and validated at application startup, so that default placeholder secrets cannot run in deployment environments.

**Why this priority**: Hardcoded repository secrets expose cryptographic tokens and database credentials to anyone with repository access.

**Independent Test**: Start the application container without setting `JWT__Secret` or with a known placeholder value; the host process must terminate immediately with a clear error message.

**Acceptance Scenarios**:
1. **Given** an environment where `JWT__Secret` is missing or matches known development placeholder patterns, **When** the application bootstraps, **Then** startup fails immediately with a fatal configuration exception.
2. **Given** secure environment variables configured via container or host environment, **When** the application starts, **Then** secrets are bound securely into configuration without plaintext repository file persistence.

---

### User Story 6 - Scoped Audit Log Visibility (Priority: P2)

As an organization administrator, I want audit logs to be restricted strictly to administrative roles, so that standard members cannot inspect organizational audit trails or perform internal reconnaissance.

**Why this priority**: Upholds the principle of least privilege and prevents internal reconnaissance by low-privilege organization members.

**Independent Test**: Request the organization audit log endpoint as a Member role user; verify that the endpoint returns 403 Forbidden, and only authenticated Admin role users receive the audit log dataset.

**Acceptance Scenarios**:
1. **Given** an authenticated user with the Member role, **When** they attempt to access the organization audit log endpoint, **Then** access is denied with 403 Forbidden.
2. **Given** an authenticated user with the Admin role, **When** they query organization audit logs, **Then** they receive full audited events for their active organization.

---

### User Story 7 - Core Security Test Suite & Automated CI Quality Verification (Priority: P3)

As a software maintainer, I want automated unit and integration tests covering security-critical boundaries (RBAC, share limits, 2FA) along with frontend build checks in CI, so that regressions are caught automatically on every pull request.

**Why this priority**: Guarantees ongoing reliability and proves security assertions through repeatable tests.

**Independent Test**: Execute `dotnet test` and verify that tests for RBAC, share expiration, and 2FA run and pass, and CI configuration executes both frontend and backend builds.

**Acceptance Scenarios**:
1. **Given** the test project executed via CI, **When** security assertions evaluate RBAC enforcement and share link expiry, **Then** all tests pass with deterministic results.
2. **Given** the continuous integration pipeline, **When** triggered on a commit, **Then** it validates both backend compilation/tests and frontend build packaging (`npm run build`).

### Edge Cases

- **Expired Share Link**: An anonymous user attempts to download a file with an expired share token; the server returns HTTP 410 Gone or 404 Not Found.
- **Max Download Count Exceeded**: A share link configured with a 3-download limit receives a 4th request; access is blocked and the link is deactivated.
- **Expired/Reused Download Ticket**: A user requests a download with a one-time ticket that has already been consumed or has expired (> 60 seconds old); the server rejects the request with HTTP 401/403.
- **Mismatched Content-Type Spoofing**: An attacker renames `malicious.exe` to `photo.png`; server magic byte inspection detects binary header mismatch and aborts stream consumption.
- **Deleted Resource Share**: A share link points to a resource that has been soft-deleted or permanently removed; link resolution safely yields 404 without leaking metadata.
- **Concurrent Rate Limiting**: Distributed bursts of 20 requests across different IP headers targeting the same account; rate limiter prevents race conditions in credential verification.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST eliminate the unauthenticated static file server middleware for `/uploads` and route all file streaming through an authenticated API endpoint supporting both `Bearer` token headers and short-lived one-time download tickets (`?ticket=...`).
- **FR-002**: System MUST verify both organization tenancy (`OrganizationId`) and user directory access permissions before serving any file stream via `IStorageProvider`.
- **FR-003**: System MUST require `[Authorize(Policy = "CanShare")]` and assert `Resource.OrganizationId == User.OrganizationId` when generating share links.
- **FR-004**: System MUST enforce rate limiting on `/api/auth/login` and `/api/auth/2fa/*` endpoints with a maximum of 10 requests per minute per IP address.
- **FR-005**: System MUST validate file uploads using magic byte inspection (header sniffing) and disallow raw execution of scriptable file types (such as SVG) without `attachment` disposition and `nosniff`.
- **FR-006**: System MUST persist root directory file uploads with a database `null` foreign key rather than `Guid.Empty`.
- **FR-007**: System MUST load JWT signing secrets and database credentials from environment variables, failing startup if the secret is absent, insecure (< 32 bytes), or matches default placeholder strings.
- **FR-008**: System MUST enforce role-based authorization restricting organizational audit log retrieval strictly to users possessing the Admin role (`[Authorize(Roles = "Admin")]`), returning 403 Forbidden to standard Members.
- **FR-009**: System MUST provide an automated test project containing automated tests covering RBAC checks, share token expiration, download limits, and 2FA verification.
- **FR-010**: System MUST configure CI pipelines to build both the frontend application and backend test suite.
- **FR-011**: System MUST remove legacy or unneeded packages (`Microsoft.AspNetCore.SignalR 1.1.0`, `Cors 2.2.0`) and purge repository hygiene artifacts (`.pptx`, out-of-scope markdown files).

---

### Key Entities

- **Resource**: Stored file or link metadata with properties: `Id`, `OrganizationId`, `DirectoryId` (nullable `Guid?`), `StoragePath`, `ContentType`, `SizeBytes`, `CreatedAt`.
- **DownloadTicket**: Short-lived, single-use signed token for browser downloads: `Token`, `ResourceId`, `UserId`, `ExpiresAt`, `IsUsed`.
- **ShareLink**: Public or restricted share token with properties: `Id`, `ResourceId`, `OrganizationId`, `Token`, `PasswordHash`, `ExpiresAt`, `MaxDownloads`, `DownloadCount`, `IsActive`.
- **AuditLog**: Security and administrative event record with properties: `Id`, `OrganizationId`, `UserId`, `Action`, `ResourceDetails`, `Timestamp`, `IpAddress`.
- **StorageProvider**: Abstraction for persistent file storage (`GetAsync`, `SaveAsync`, `DeleteAsync`), abstracting local disk or cloud bucket drivers.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of direct unauthenticated HTTP requests to `/uploads/...` return 401 Unauthorized or 404 Not Found.
- **SC-002**: 0 cross-organization resource share links can be generated across tested tenant boundaries.
- **SC-003**: 100% of brute-force attempts exceeding 10 requests per minute to authentication endpoints receive HTTP 429 Too Many Requests.
- **SC-004**: 100% of uploaded files disguised with incorrect MIME types are rejected before storage persistence.
- **SC-005**: Application container fails startup in under 2 seconds if JWT secret is missing or default.
- **SC-006**: CI pipeline passes with 100% automated test success and clean frontend production build artifact verification.

---

## Assumptions

- **Storage Provider**: `IStorageProvider.GetAsync` exists in the codebase and can be leveraged directly for authenticated file streaming without requiring third-party cloud SDK rewires for local dev.
- **Identity Framework**: The project uses ASP.NET Core Identity / JWT bearer tokens where `OrganizationId` is present in user claims or can be derived from the user session context.
- **Database Engine**: PostgreSQL with Entity Framework Core migrations is used for the database schema.
- **Rate Limiting Technology**: ASP.NET Core built-in rate limiting middleware (`Microsoft.AspNetCore.RateLimiting`) introduced in .NET 7/8 is utilized.
